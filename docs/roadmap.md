# 開発計画と決定事項

## 進め方

小さく作り、実際に使ってから次の機能を追加する。[プロダクト構想](product-concept.md)のMVP全体と、最初のリリースは区別する。

### レビューの単位

- 原則 **1 Step = 1 PR**。一つの目的と、その確認に必要なテストに絞る。
- 目安は100〜250行、上限は原則400行程度。追加＋削除の合計で数える。手書きの実装・設定・ドキュメントを含め、テストは除外して別途行数を示す。
- **初期導入PRは行数制限の対象外**とすることがユーザーから明示的に了承済み。Laravel・Livewire・Pest・Boost・ドキュメントの初期整備を含む。
- 以降は生成ファイルやlock更新も別枠で明示する。大きくなる場合に自動的な例外扱いはせず、分割か扱いの確認を行う。
- 上限に達しそうならStepを`a`・`b`へ分割する。多くのStepを一括実装した後でコミットだけ細分化しない。
- 小さな業務ルールなどは内部機能だけのStepでもよい。画面操作が可能になった時点で、実際の操作で確認する。
- 機能追加と無関係なリファクタリングを混ぜない。レビュー完了前に次のStepを積み上げない。
- PRは [共通テンプレート](../.github/pull_request_template.md) を使い、「ユーザーストーリー」「完了条件」「実装内容」「テスト観点」「動作検証観点」を記載する。

### StepとPRを対応づける手順

共通の統合先・既定ブランチは **`main`**。`git fetch origin` 後の最新の `origin/main` からStepごとの作業ブランチを切り出し、**作業ブランチ → `main`** のPRを作成する。`main`への直接Pushは通常の開発では行わず、レビュー後にユーザーの指示・許可を受けてマージする。PR作成時は `gh pr create --base main` のようにマージ先を明示する。

1. 実装前に対象Stepを一つ選び、完了条件を具体化する。既存のStepにない作業は、まずロードマップへStepを追加する。
2. ブランチは `codex/step-<ID>-<概要>`、PRタイトルは `[Step <ID>] <変更の目的>` とする。例：`codex/step-2-4-equipment-form`、`[Step 2-4] 機材の登録画面を追加する`。
3. PR本文にStep番号と該当フェーズへのリンクを記載する。一つのPRに複数のStepをまとめない。分割時はロードマップにも `2-4a`・`2-4b` のような子Stepとそれぞれの完了条件を追加する。
4. 完了条件に `AC1`・`AC2` などの番号を付け、テスト観点・動作検証観点から対応する番号を参照する。実行結果と未実行の確認手順を区別する。
5. 差分量はPRのベースブランチとの共通祖先からの累積差分で確認する。最新コミットだけが400行以内でも、PR全体が超えていれば分割する。
6. PR作成後、下の対応表にPRリンクと状態を記録する。PR作成やPushだけでStepを完了にせず、完了条件を満たしてレビュー・マージされた時点で完了とする。
7. 次のStepは現在のPRがマージされた後に着手する。先に進める必要がある場合はユーザーの指示に従う。

各項目は小さな変更なら1〜3行でよい。対象外は理由を一言添え、テスト種別を埋めるためだけに不要なテストを追加しない。基盤変更のユーザーストーリーは開発者・レビュアーを主語にしてよい。これらはCodexの作業ルールとテンプレートによる運用であり、現時点ではCIによる強制チェックは行わない。

## 現在の段階：機材と種目を用意する

認証必須のToday画面とログアウトまで整備済み。最初に使うレッグプレスを登録できるよう、機材の定義から実装する。

## 最初に使える範囲（合意済み）

**ログイン → 機材・種目登録 → フリーで筋トレ記録 → 終了 → 次回に前回実績表示。**

- メールアドレス＋パスワード認証。一般向け新規登録は用意せず、自分のアカウントを初期作成する。
- 機材と種目の登録・編集。
- フリートレーニング開始、種目追加、重量・回数・セットの記録、終了。
- セット完了ごとに保存。画面を閉じても途中から再開できる。
- 種目ごとの前回実績をトレーニング画面に表示。
- 最初からUser境界を設ける。
- Android ChromeとPC Chromeで確認。オンライン前提。

初期アカウントの実際のメール・パスワードはソースに書かず、作成方法を認証実装時に用意する。

Phase 9完了を当初MVPの完成とする。Googleログイン、Fitbit、休憩タイマー、高度な分析などは完成条件に含めず、別の計画として扱う。

## 最初のサンプル

| 項目 | 値 | 状態 |
| --- | --- | --- |
| 機材・種目 | レッグプレス | ユーザー提供 |
| 機材カテゴリ | マシン | ユーザー提供 |
| 重量単位・増分 | kg・9kg | ユーザー提供 |
| 記録方式 | 重量＋回数 | 方針 |
| 初期目標 | 10回×2セット、変更可能 | 会話での提案値 |
| 初回重量 | 利用者が入力する | 自動決定しない |

Step 2-1時点では、機材名は前後の空白を除いて1〜100文字、カテゴリはマシン・フリーウェイト・有酸素・その他、重量単位はkgとする。重量増分は0.01〜999.99の正数で小数2桁まで保持する。時間・距離を扱う機材の単位や増分の任意化は、Phase 6で実際の記録方式と合わせて決める。

10回×2セットは、[ACSMの一般向け資料](https://www.acsm.org/docs/default-source/files-for-resource-library/resistance-training-for-health.pdf)の8〜12回・2〜3セットを参考に、短時間の継続を重視した初期案。レッグプレス固有の最適値や個別の運動処方ではない。9kg刻みは入力補助に使い、達成すれば必ず9kg増量するルールにはしない。

## 必要になった段階で確認すること

- 前回実績：途中のトレーニングや過去記録の編集をどう扱うか。同じ種目を一日に複数回実施した場合の基準。
- 記録：セットの修正・削除、中断・終了、日付をまたぐ場合の扱い。
- 目標提案：達成判定、増量幅、複数回の実績を使うか、未達時の挙動。
- 成長表示：自己ベスト、重量・回数推移の指標と集計単位。
- UI：色・雰囲気、主要ナビゲーション、実際の端末での使い勝手。
- 運用：CloudのDB・リージョン・見積もり・バックアップ・支出制限。

これらを未確認のまま確定仕様として実装しない。今の小さな実装に必要な項目から確認する。
